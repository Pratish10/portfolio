The Problem

Restaurant chains needed a unified platform to manage QR-code-based ordering across multiple branches with separate admin and customer interfaces, secure authentication, and the ability to handle concurrent ordering load.

Context

Built as an independent project to demonstrate full-stack SaaS architecture. QR Dine serves restaurant administrators and end customers across multiple branches from a single multi-tenant platform.

Architecture

Multi-tenant Next.js frontend with separate admin and client surfaces shares a Node.js API layer. MongoDB stores restaurant, menu, and order data partitioned by branch. JWT tokens carry role claims (admin/customer) validated on every API route.

Engineering Decisions

Engineering decision

JWT + RBAC vs. Session-Based Authentication

Situation: Two separate frontend apps (admin and customer) sharing a single API without shared session state.

Option A

Server-side session store — stateful, easy to invalidate, requires shared session infrastructure between frontend surfaces.

Option B

Chosen

JWT with role claims — stateless, works natively across separate frontend origins without session sharing.

Rationale: Two frontend apps sharing one API without a shared session store made stateless JWT the natural fit. Role claims embedded in the token meant the API could authorize any request without a session lookup.

Trade-off: JWTs cannot be invalidated before expiry. Mitigated with short expiry (15 min) and refresh token rotation.

Result: Clean role-based access control across admin and customer surfaces. API authorization consistent and stateless.

Challenges

  • ›Multi-tenant data isolation required careful MongoDB schema design to prevent cross-branch data leakage

Lessons Learned
