Enterprise Azure Integration

ByBar Azure Integration Pipeline

End-to-end Azure integration pipeline for a live Netherlands fashion brand — processing 10–20 million product records per sync with end-to-end latency under 4 seconds, fully deployed as infrastructure-as-code.

10–20M product records per sync<4s end-to-end pipeline latency100% infrastructure as code via Azure BicepZero-touch deployment via Azure DevOps YAML

The Problem

A Netherlands-based fashion enterprise (ByBar) needed a reliable, high-throughput pipeline to sync 10–20 million product records into their downstream product management system — with data transformation, schema validation, and guaranteed delivery, all repeatable across environments.

Context

B2B enterprise integration where data integrity and latency are business-critical. The client operates at EU enterprise scale — data volumes are large, transformation rules are complex (XSLT), and the integration must be environment-agnostic and deployable by pipeline, not manually.

My Role

Sole architect and implementer — designed the integration architecture, wrote the XSLT transformations, defined the Canonical Data Model, configured all Azure services, and deployed everything via Bicep and Azure DevOps YAML pipelines.

  • Designed end-to-end integration architecture: recurrence trigger → Logic App → XSLT transformation → Canonical Data Model → Azure Blob Storage → Azure Service Bus → downstream consumer
  • Wrote XSLT transformations to map source product schema to the Canonical Data Model — handling 10–20 million records per sync with structural validation
  • Configured and deployed Azure Logic Apps, Service Bus, Blob Storage, APIM, and Event Grid
  • Deployed entire integration infrastructure as code using Azure Bicep — repeatable, environment-agnostic release workflows across dev, staging, and production
  • Set up Azure DevOps Pipelines with YAML for automated deployment and release orchestration

Architecture

Recurrence-triggered Azure Logic App ingests the product feed, passes records through an XSLT transformation layer that maps source schema to a Canonical Data Model (CDM). Transformed records are written to Azure Blob Storage for durability, then published to Azure Service Bus for ordered, guaranteed delivery to the downstream product management system. The entire infrastructure — Logic Apps, APIM, Event Grid, Service Bus — is defined in Azure Bicep and deployed via Azure DevOps YAML pipelines for environment-agnostic, repeatable releases.

Engineering Decisions

Engineering decision

XSLT Transformation vs. Code-Based Mapping

Situation: The product records required complex structural transformation from the source schema to the Canonical Data Model. Two approaches were viable: declarative XSLT or imperative C# mapping code.

Option A

C# code-based mapping — explicit control, easier to unit test individual fields, familiar language for the team.

Option B

Chosen

XSLT transformation — declarative, schema-portable, natively supported by Logic Apps without additional runtime dependencies.

Rationale: XSLT integrates natively with Azure Logic Apps and is designed exactly for structured document transformation at this scale. Keeping transformation declarative and outside application code means schema changes are isolated and don't require redeployment of backend services.

Trade-off: XSLT is less familiar to most developers and harder to debug than C# code. Requires investment in XSLT tooling and understanding of XPath.

Result: Transformation pipeline processes 10–20 million records per sync within the 4-second end-to-end SLA. Schema changes are applied without service redeployment.

Engineering decision

Bicep IaC vs. Manual Azure Portal Configuration

Situation: The integration uses 5 Azure services. The question was whether to configure them through the Azure Portal or define them entirely as Infrastructure-as-Code using Bicep.

Option A

Azure Portal configuration — faster initial setup, no Bicep learning curve, sufficient for a single environment.

Option B

Chosen

Azure Bicep IaC — all services defined declaratively, version-controlled, deployable to any environment via pipeline.

Rationale: An EU enterprise client requires a production-grade, auditable, repeatable deployment. Manual portal configuration creates environment drift and makes disaster recovery and staging parity impossible to guarantee.

Trade-off: Bicep adds upfront authoring time and requires understanding ARM template structure. Worth it for any multi-environment or production-grade integration.

Result: Entire integration stack — Logic Apps, APIM, Event Grid, Service Bus — deployable from a single Bicep + YAML pipeline run. Zero environment drift between staging and production.

Challenges

  • ›Handling 10–20 million records reliably within a 4-second SLA required careful choice of Service Bus partitioning and session handling to prevent message ordering issues at scale
  • ›XSLT transformation for deeply nested product schemas required iterative validation against real production data — source schema had undocumented edge cases that only surfaced at volume

Outcome

Production integration pipeline serving a live EU enterprise client. 10–20 million product records per sync processed end-to-end in under 4 seconds. Entire infrastructure deployable via a single pipeline run — environment-agnostic, observable, repeatable.

Lessons Learned

  • —At enterprise data volumes, choosing the right Azure primitive (Service Bus vs Storage Queue vs Event Grid) is an architecture decision with significant downstream consequences — getting it right upfront saves re-architecture later
  • —IaC from day one is not optional on multi-environment enterprise integrations — the overhead of Bicep authoring is repaid on the first staging → production deployment
