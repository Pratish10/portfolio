Engineering Decisions

Engineering decision

Node.js → .NET Core: Full Rebuild vs. Incremental Refactor

Situation: The Node.js backend had pervasive monolithic structure — data shapes, business logic, and infrastructure concerns deeply coupled. The question was whether to refactor incrementally or rebuild with a proper architecture.

Option A

Incremental refactor of existing Node.js — lower risk, gradual improvement, no big-bang rewrite risk.

Option B

Chosen

Full rebuild in .NET Core Clean Architecture — clear domain boundaries, proper async model, type safety, and testability from the ground up.

Rationale: The monolithic coupling meant any incremental refactor would carry the structural debt forward. Clean Architecture in .NET Core enabled proper separation of domain, application, and infrastructure layers — making multi-threading and caching safe to add without unintended side effects.

Trade-off: Full rebuild carries rewrite risk and requires feature parity validation against production. Mitigated by phased rollout with existing Node.js as fallback.

Result: 10× throughput improvement. API response from 10s → 300ms. Platform supporting 500+ concurrent users across 4 brokers with no regression in functionality.

Engineering decision

Auth Redesign: Access + Refresh Token vs. Session-Based

Situation: The legacy auth layer was insecure and had no concept of broker-level session isolation — a critical risk for a multi-broker financial platform.

Option A

Server-side session store — stateful, easy to invalidate immediately, familiar pattern.

Option B

Chosen

Access + refresh token architecture with RBAC and broker-level session isolation — stateless, horizontally scalable, granular authorization.

Rationale: A multi-broker trading platform where different users have different broker permissions required token-level authorization claims. Broker-level session isolation is only achievable cleanly with JWTs carrying broker scope claims — sessions would require complex session-to-broker mapping.

Trade-off: Access tokens cannot be invalidated before expiry. Mitigated with short-lived access tokens (15min) and refresh token rotation with revocation on broker permission changes.

Result: Clean, stateless authorization across all trading workflows. Broker-level session isolation enforced at the token claim level — no cross-broker data leakage possible.

Outcome

Production trading platform with 10× throughput improvement, 97% API latency reduction (10s → 300ms), sub-second UI load, and secure multi-broker authorization. Serving 80–100 daily active users under live financial conditions.

Lessons Learned

  • —Clean Architecture is not just a pattern preference — for a fintech system with multi-threading and multiple broker integrations, proper domain/infrastructure separation is what makes safe concurrent programming achievable
  • —JWT broker-level session isolation must be designed before the first line of auth code is written — retrofitting broker claims onto an existing token structure is error-prone under production pressure
